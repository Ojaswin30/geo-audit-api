# GEO Audit API

A backend API that audits any public webpage for AI search visibility and recommends structured JSON-LD schema markup — built for Villion's GEO (Generative Engine Optimization) platform vision.

---

## What It Does

Send a URL → get back:
- Page title, meta description, headings, image
- Recommended schema type (Article / Product / Organization)
- A fully populated JSON-LD block generated by an LLM
- A fallback rule-based JSON-LD block if the LLM is unavailable

---

```bash

```

Create a `.env` file inside `backend/`:


## API Reference

### `POST /audit`

Audits a public webpage and returns structured data recommendations.

**Request body:**
```json
{
  "url": "https://stripe.com"
}
```

**Response:**
```json
{
  "url": "https://stripe.com/",
  "title": "Stripe | Financial Infrastructure to Grow Your Revenue",
  "meta_description": "Stripe is a financial services and payments platform...",
  "headings": ["Financial infrastructure to grow your revenue.", "..."],
  "image_url": "https://images.stripeassets.com/...",
  "schema_type": "Organization",
  "json_ld": {
    "@context": "https://schema.org",
    "@type": "Organization",
    "name": "Stripe",
    "url": "https://stripe.com",
    "description": "...",
    "sameAs": ["https://twitter.com/stripe", "https://linkedin.com/company/stripe"]
  },
  "llm_used": true,
  "error": null
}
```

**Error handling:**

| Scenario | Behavior |
|---|---|
| Invalid URL format | 422 Validation Error via Pydantic |
| Page unreachable / timeout | 422 with descriptive message |
| HTTP 404 / 5xx from target | 422 with HTTP status code |
| LLM call fails | Falls back to rule-based JSON-LD, `llm_used: false` |
| LLM returns malformed JSON | Strips markdown fences and retries parse |

## Design Decision Log

### 1. FastAPI over Flask

FastAPI was chosen for its native Pydantic integration, automatic OpenAPI documentation, and async support. For a scraping API where I/O latency is the bottleneck, async readiness matters at scale. Flask would have required additional libraries to achieve the same validation and documentation quality.

### 2. BeautifulSoup over Playwright

BS4 with Requests is synchronous, lightweight, and sufficient for static HTML pages. Playwright (headless browser) is the right choice for JavaScript-rendered SPAs but adds significant overhead — longer cold starts, higher memory usage, and more complex deployment. The trade-off: this implementation will fail silently on heavily JS-rendered pages (e.g., React SPAs with no SSR). Documented in Known Limitations.

### 3. Rule-based schema type detection + LLM for content generation (hybrid approach)

This is the most important design decision in the project.

**Schema type detection is rule-based** — fast keyword matching against title, meta description, and headings. This is intentional: determining whether a page is an Article, Product, or Organization is largely a pattern-matching problem. It's deterministic, free, and runs in microseconds. Using an LLM for this would add latency and cost with no meaningful quality gain.

**JSON-LD content generation uses the LLM** — populating fields like `founder`, `sameAs`, `datePublished`, `offers.price`, etc. requires understanding the semantic meaning of the page, not just its structure. This is exactly where LLMs add value. Rule-based logic cannot reliably extract and map these fields from unstructured page text.

This split reflects a broader principle: use deterministic logic where the problem is well-defined, use LLMs where ambiguity and semantic understanding are required.

### 4. Graceful LLM fallback

If the LLM call fails for any reason (quota exceeded, network error, malformed output), the API still returns a valid response with a minimal rule-based JSON-LD block and `llm_used: false`. This ensures the API never fully breaks — important for a product that clients depend on.

### 5. `raw_text` extracted but never exposed in response

The scraper extracts up to 3000 characters of page text purely for LLM context. It is intentionally excluded from the API response to keep the payload clean and avoid exposing potentially large blobs of scraped content to clients.

## How This Supports Villion's GEO Vision

GEO (Generative Engine Optimization) is about making web content more legible to AI-powered search engines like Perplexity, ChatGPT search, and Google's AI Overviews. These engines rely heavily on structured data (JSON-LD) to understand and cite content accurately.

This API directly addresses that problem: it automates the audit and recommendation layer that tells a business *what structured markup they're missing and what it should contain*. The LLM layer makes the recommendations contextually accurate rather than generic — the difference between a JSON-LD block that says `"name": "Unknown"` and one that says `"founder": "Patrick Collison", "sameAs": ["https://twitter.com/stripe"]`.

At scale, this becomes the foundation of a bulk audit pipeline that can process entire websites and generate actionable structured data recommendations.

## Scale-Up Architecture (50+ Pages)

Single-URL auditing works fine as a prototype. Auditing an entire website at scale requires a fundamentally different architecture:

```
                        ┌─────────────────┐
                        │  Coordinator    │
                        │  Agent          │
                        │  (URL queue)    │
                        └────────┬────────┘
                                 │
               ┌─────────────────┼─────────────────┐
               ▼                 ▼                 ▼
        ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
        │  Scraper    │   │  Scraper    │   │  Scraper    │
        │  Worker 1   │   │  Worker 2   │   │  Worker N   │
        └──────┬──────┘   └──────┬──────┘   └──────┬──────┘
               └─────────────────┼─────────────────┘
                                 ▼
                        ┌─────────────────┐
                        │  LLM Agent      │
                        │  (schema gen)   │
                        │  Rate-limited   │
                        └────────┬────────┘
                                 ▼
                        ┌─────────────────┐
                        │  Results DB     │
                        │  (PostgreSQL)   │
                        └─────────────────┘
```

Key decisions at scale:

- **Celery + Redis** for task queuing — scraper workers pull URLs from the queue in parallel
- **LLM only where needed** — rule-based detection still handles schema type; LLM only runs on pages that pass a content quality threshold (e.g., has sufficient text)
- **Failure handling** — failed URLs go to a dead-letter queue for retry, not dropped silently
- **Caching** — Redis cache on URL hash so the same page isn't re-audited within a TTL window
- **Rate limiting** — LLM calls are batched and rate-limited to stay within API quotas

## Known Limitations

| Limitation | Impact | Fix with more time |
|---|---|---|
| BS4 fails on JS-rendered pages | Silent empty results for SPAs | Add Playwright as fallback when BS4 returns no headings |
| No caching | Same URL re-scraped on every request | Redis cache keyed on URL hash |
| LLM output not schema.org validated | JSON-LD may have invalid fields | Add `schema-org` validator library post-generation |
| Single URL only | Can't audit entire sites | Task queue architecture described above |
| No authentication | API is open | Add API key header middleware |
| Heading deduplication missing | Duplicate headings appear in response | Deduplicate in scraper before returning |
